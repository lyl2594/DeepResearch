## 项目概述

本项目是一个基于大语言模型的多Agent协同深度研究系统。系统接收用户的研究问题后，由协调器（Coordinator）判断意图，规划器（Planner）拆解研究计划，研究员（Researcher）自主调用工具执行搜索/编码/检索，评估器（Eval）质检研究质量，报告员（Reporter）综合产出研究报告。整个流程支持SSE流式推送、人机协同审核（HITL）、会话历史回放、步骤跳过控制，并叠加了可观测健壮性、MCP动态工具扩展、RAG私有知识检索三大横切能力。

**技术栈**：Python 3.13 + FastAPI + LangGraph + LangChain + PostgreSQL + Next.js + React + TypeScript

## 责任一：前期技术选型与架构设计

### 实现了什么功能

在项目启动阶段，完成整体技术架构选型、模块划分、开发规范制定，为后续10个月的迭代开发奠定基座。

### 实现思路

围绕"AI Agent自主研究"这一核心场景，从三个维度做架构决策：

| 维度 | 决策 | 理由 |
|------|------|------|
| **工作流引擎** | LangGraph | 原生支持图结构编排、状态持久化、HITL中断恢复，比自研状态机省力 |
| **通信协议** | SSE（Server-Sent Events） | 单向流式推送，比WebSocket轻量；浏览器原生支持，无需额外依赖 |
| **持久化** | PostgreSQL双存储 | 业务表存"产品可见数据"（对话历史、事件流水），checkpoint表存"开发态resume状态" |

### 技术亮点

- **前后端解耦的SSE契约**：后端五层调用链产出标准SSE帧，前端通过统一的`ChatEvent`类型消费，实时流和回放流在消费端完全一致，无需`if (isReplay)`判断
- **双存储策略**：业务表（`chat_streams`）和LangGraph checkpoint表各司其职——前者支持刷新/重启后回看，后者支持HITL中断后恢复，互不干扰

### 实操流程

```
1. 调研阶段（2周）
   → 评估 LangGraph / AutoGen / CrewAI 三个Agent框架
   → 选定 LangGraph（图编排+checkpoint+HITL原生支持）

2. 架构设计（2周）
   → 划分模块：server / graph / rag / tools / database / utils
   → 定义 State 数据结构（messages / current_plan / observations / final_report）
   → 设计 SSE 五层调用链：endpoint → generator → stream_graph_events → process_chunk → make_event

3. 规范制定（1周）
   → 异步优先：所有节点用 async def，I/O 用 await
   → 配置穿透：Configuration 从 config 参数解析，不硬编码
   → 落库容错：数据库写入失败不影响流式推送
```

## 责任二：SSE流式推送五层架构与LangGraph工作流编排

### 实现了什么功能

将大模型的研究过程（可能持续几十秒到几分钟）以**逐token流式推送**的方式实时呈现给前端，用户能看到打字机效果、工具调用过程、研究计划审核中断，而不是等待最终结果。

### 实现思路

设计**五层调用链**，每层单一职责，数据从HTTP请求逐层转换为SSE帧：

```
Layer 1: chat_stream（前台接待）
  → 收HTTP请求、生成thread_id、返回StreamingResponse(SSE)

Layer 2: _astream_workflow_generator（翻译官）
  → 判断新对话/HITL resume → 组装workflow_input/config → yield转发

Layer 3: _stream_graph_events（执行引擎）
  → graph.astream()执行图 → 分流interrupt/messages事件 → 异常兜底

Layer 4: _process_message_chunk（分拣员）
  → 判断消息类型（HumanMessage/ToolMessage/AIMessageChunk）
  → 转换为 message_chunk/tool_calls/tool_call_result 事件

Layer 5: _make_event（打包发货+存档）
  → JSON序列化 → 落库chat_streams表 → 拼SSE帧字符串
```

### 技术亮点

| 亮点 | 说明 |
|------|------|
| **五层单一职责** | 每层可独立测试、独立复用（`_make_event`被回放功能复用）、独立扩展 |
| **HITL resume双分支** | Layer 2判断是新对话（`{messages}`）还是恢复对话（`Command(resume=feedback)`），支持计划审核/报告审核中断后恢复 |
| **三流模式消费** | `graph.astream(stream_mode=["messages","updates"], subgraphs=True)` 同时消费消息流、状态更新流、子图事件，拿到ReAct Agent内部多轮工具调用 |
| **落库容错** | Layer 5的数据库写入用try/except包裹，落库失败只打warning日志，不影响SSE帧正常推送 |
| **事件类型完备** | 覆盖 message_chunk / tool_calls / tool_call_result / interrupt / error 五种事件类型，前端可完整还原研究过程 |

### 实操流程

```
执行前（用户输入问题）：
┌──────────────────────────────────────────────────┐
│ 用户输入："光速是多少？"                            │
│ 前端封装 ChatRequest { messages, thread_id? }     │
└──────────────────────────────────────────────────┘

执行过程（五层链逐层处理）：
Layer 1: 收请求 → 生成thread_id → 返回StreamingResponse
    ↓
Layer 2: 判断新对话 → 组装workflow_input={messages,...}
         组装workflow_config={thread_id, max_plan_iterations,...}
    ↓
Layer 3: graph.astream()执行图
         → coordinator判断意图（研究vs闲聊）
         → planner拆解研究计划
         → human_feedback中断等待用户审核计划
         → researcher调用web_search/crawl_tool执行搜索
         → reporter综合observations生成报告
    ↓
Layer 4: 图产出的AIMessageChunk → "message_chunk"事件
         图产出的ToolMessage → "tool_call_result"事件
         图产出的interrupt → 直接给Layer 5
    ↓
Layer 5: JSON序列化 → INSERT chat_streams → 拼"event: X\ndata: {json}\n\n"

执行后（浏览器渲染）：
┌──────────────────────────────────────────────────┐
│ event: message_chunk                              │
│ data: {"content":"光速是299792458米/秒"}           │
│ → 浏览器逐字渲染，打字机效果                        │
│ → chat_streams表同步落库（可回放）                  │
└──────────────────────────────────────────────────┘
```

## 责任三：可观测健壮性建设

### 实现了什么功能

在研究流程运行过程中，实现**每个图节点耗时可见**、**数据库有等待边界**、**LLM调用不卡死**三大可观测与健壮性能力，解决"流程卡住了但不知道卡在哪"的线上排障难题。

### 实现思路

从三个层面叠加横切能力，不侵入业务逻辑：

#### 3.1 @timed_node 装饰器 — 节点耗时观测

```python
def timed_node(func):
    @functools.wraps(func)
    async def _async_wrapper(*args, **kwargs):
        start = time.perf_counter()
        try:
            return await func(*args, **kwargs)
        finally:
            logger.info(f"[timing] {func.__name__}: {time.perf_counter() - start:.2f}s")
    return _async_wrapper if asyncio.iscoroutinefunction(func) else _sync_wrapper
```

**思路**：用装饰器横切统计节点耗时，`finally`块保证**异常节点也记录耗时**（异常节点正是需要定位的慢节点）。用`time.perf_counter()`单调时钟，不受系统时间调整影响。

#### 3.2 CB-2 连接池加固 — 数据库等待边界

```python
engine = create_engine(
    DATABASE_URL,
    pool_size=10,           # 常驻连接
    max_overflow=20,        # 突发溢出
    pool_recycle=3600,      # 1小时回收
    pool_pre_ping=True,     # 用前ping防断连
    connect_args={
        "connect_timeout": 10,               # 建连10s超时
        "options": "-c statement_timeout=30000",  # SQL执行30s熔断
    },
)
```

**思路**：六参数覆盖连接池生命周期——`pool_size`+`max_overflow`控制连接数上限，`pool_recycle`防止PG端断连后僵尸连接，`pool_pre_ping`取连接前先`SELECT 1`确认存活，`connect_timeout`+`statement_timeout`给建连和查询设硬性超时边界。

#### 3.3 LLM 超时熔断 — 模型调用不卡死

```python
merged.setdefault("max_retries", 3)                          # 限流自动重试3次
merged.setdefault("timeout", int(os.getenv("LLM_TIMEOUT", "60")))  # 60s超时
```

**思路**：`timeout=60s`防LLM API卡死，`max_retries=3`处理429限流，环境变量`LLM_TIMEOUT`可按模型调整。

### 技术亮点

| 亮点 | 说明 |
|------|------|
| **finally保证异常可观测** | `@timed_node`的`finally`块确保节点抛异常时耗时也记录，不遗漏慢节点 |
| **单调时钟精确计时** | `perf_counter()`纳秒级精度，不受NTP校时跳变影响 |
| **六参数连接池** | CB-2覆盖连接数/溢出/回收/预检/建连超时/SQL超时全生命周期 |
| **PG MVCC天然并发** | PostgreSQL的MVCC读不阻塞写，不需要SQLite的WAL补丁 |
| **双保险LLM调用** | timeout防卡死 + retries防限流，环境变量可覆盖 |

### 实操流程

```
部署前（无可观测，排障困难）：
┌──────────────────────────────────────────────────┐
│ 研究流程卡住了                                     │
│ 日志：[researcher] 执行步骤: "光速测量"             │
│       [researcher] 搜索成功                        │
│ 问题：哪个节点慢？不知道。LLM卡了还是DB卡了？不知道  │
└──────────────────────────────────────────────────┘

部署后（三层可观测）：
┌──────────────────────────────────────────────────┐
│ 日志输出：                                        │
│   [timing] coordinator_node: 0.52s               │
│   [timing] planner_node: 1.23s                    │
│   [timing] researcher_node: 2.35s                 │
│   [timing] eval_node: 3.21s    ← 慢节点定位！      │
│   [timing] reporter_node: 1.08s                   │
│                                                   │
│ DB层：statement_timeout=30s → 慢SQL自动熔断        │
│ LLM层：timeout=60s → API卡死60s后超时报错          │
│                                                   │
│ 一眼看出 eval_node 耗时最长，可针对性优化           │
└──────────────────────────────────────────────────┘

实操步骤：
1. @timed_node 装饰 researcher_node / coder_node / reporter_node 等关键节点
2. create_engine 配置 CB-2 六参数
3. get_llm_by_type 增加 timeout + max_retries
4. 启动服务，观察日志中 [timing] 输出
```

## 责任四：MCP动态工具集成与RAG私有知识检索

### 实现了什么功能

#### 4.1 MCP动态工具集成

实现**新工具上线不用改代码**——通过MCP（Model Context Protocol）协议，运行时动态加载外部工具服务器提供的工具，注入到Agent的工具列表中。支持stdio/sse/streamable_http三种传输方式，内置安全门防止未授权工具注入。

#### 4.2 RAG私有知识检索

实现**私有知识库可检索**——通过Retriever抽象层隔离不同知识库provider（内存/ES/AIHub），Agent可调用`local_search_tool`检索组织内部文档。前端提供6个API端点管理知识库配置（CRUD+连接测试+资源查询）。

### 实现思路

#### MCP部分：双层安全门 + 限时降级加载

```
第一层安全门（全局开关）：
  ENABLE_MCP_SERVER_CONFIGURATION=false（默认）
  → 所有MCP请求直接403（stdio transport可执行任意命令，必须默认关）

第二层安全门（agent筛选）：
  每个MCP server配置 add_to_agents: ["researcher"]
  → 只有researcher节点加载该server的工具
  → coder节点不会拿到查天气的工具

限时加载 + 降级：
  asyncio.wait_for(client.get_tools(), timeout=60)
  → ImportError → return []（未装适配库）
  → TimeoutError → return []（60s超时）
  → Exception → return []（其他异常）
  → 所有失败返回空列表，研究流程不受影响
```

#### RAG部分：开闭原则的Retriever抽象

```python
class Retriever(abc.ABC):
    @abc.abstractmethod
    def list_resources(self, query=None) -> list[Resource]: ...

    @abc.abstractmethod
    def query_relevant_documents(self, query, resources=None) -> list[Document]: ...
```

**思路**：定义两个抽象方法的契约，新provider（ES/向量库/AIHub）只需继承实现，不需要改调用方代码。`build_retriever_by_configs`工厂方法按配置选择provider，`RetrieverTool`封装为LangChain工具注入Agent。

### 技术亮点

| 亮点 | 说明 |
|------|------|
| **MCP双层安全门** | 全局开关（默认关）+ agent筛选（`add_to_agents`），防止未授权工具注入 |
| **MCP三层降级** | ImportError/TimeoutError/Exception全部返回`[]`，MCP失败不破坏主流程 |
| **MCP工具来源标注** | `description`加`Powered by '<server>'`前缀，便于审计追溯 |
| **MCP白名单过滤** | 只保留`transport/command/args/url/env/headers`启动参数，防额外字段TypeError |
| **RAG开闭原则** | `Retriever` ABC定义契约，新provider实现两方法即可接入，不改调用方 |
| **RAG-web协同** | `local_search_tool`空结果时LLM自主转向`web_search`，本地和公网无缝切换 |
| **RAG配置持久化** | 6端点CRUD + PG `rag_configs`表，前端可配置管理，不用改代码重新部署 |
| **RAG人工审核** | `human_retriever_node`用`interrupt`暂停流程，用户可修改关键词/阈值后重新检索 |

### 实操流程

#### MCP工具集成流程

```
1. 运维开启MCP：设置 ENABLE_MCP_SERVER_CONFIGURATION=true
2. 前端配置MCP server：
   { transport: "stdio", command: "python",
     args: ["-m", "weather_mcp_server"],
     add_to_agents: ["researcher"],
     enabled_tools: ["get_weather"] }
3. 用户提问 → POST /api/chat/stream（携带mcp_settings）
4. chat_stream端点：is_mcp_enabled() → True（通过第一层门）
5. researcher_node执行：
   → _setup_and_execute_agent_step 检查 mcp_settings
   → agent_type="researcher" in add_to_agents → 通过第二层门
   → 白名单过滤启动参数
   → load_mcp_tools(enabled_servers, timeout=60)
   → MultiServerMCPClient 启动子进程
   → asyncio.wait_for 等待工具列表
   → 工具description加 "Powered by 'weather_server'" 前缀
   → tools.extend(mcp_tools)
   → create_agent(..., tools, ...)
6. Agent自主决定调用 get_weather 工具
7. 工具返回结果 → Layer 4转为tool_call_result事件 → 前端渲染
```

#### RAG知识检索流程

```
1. 前端配置知识库：
   POST /api/config/rag/save_config
   { name: "公司安全规范", platform: "memory",
     resources: [{title:"安全规范v2.0", chunks:["..."]}] }
   → 持久化到 rag_configs 表

2. 用户提问"公司内部安全规范是什么？"
   → POST /api/chat/stream（携带resources + enable_rag=true）

3. researcher_node执行：
   → 检查 enable_rag && resources 非空
   → build_retriever_by_configs(resources) → MemoryRetriever
   → retriever.list_resources() → [Resource(title="安全规范v2.0")]
   → make_local_search_tool(retrievers, resources)
   → tools.append(local_search_tool)
   → tools = [web_search, crawl_tool, local_search_tool]

4. Agent调用 local_search_tool("安全规范")
   → RetrieverTool._run(keywords)
   → MemoryRetriever.query_relevant_documents("安全规范")
   → 关键词匹配 → [Document(title="安全规范v2.0", chunks=[...])]
   → 返回 list[dict]（前端RetrieverToolCall组件消费）

5. human_retriever_node 中断：
   → interrupt({type: "retriever_review", review_data: {...}})
   → 前端显示审核卡片
   → 用户点击[CONTINUE] → 提交检索结果 → goto="research_team"
   → 用户修改关键词 → 重新检索

6. LLM基于检索结果生成回答 → SSE流式推送
```

## 责任五：HITL人机协同流程设计与任务管理

### 实现了什么功能

设计并实现**三处人机协同中断点**，让用户可以审核和干预AI的研究过程：

| 中断点 | 节点 | 触发时机 | 用户操作 |
|--------|------|----------|----------|
| **计划审核** | `human_feedback_node` | Planner产出研究计划后 | `[ACCEPTED]`接受 / `[EDIT_PLAN]`修改 |
| **报告审核** | `report_review_node` | Reporter产出报告后 | `[ACCEPTED]`接受 / `[CONTINUE]`继续 |
| **检索审核** | `human_retriever_node` | RAG检索出结果后 | `[CONTINUE]`接受 / 修改关键词重检 |

### 实现思路

基于LangGraph的`interrupt()`机制实现暂停-恢复：

```python
# 中断点：暂停图执行，等待用户输入
feedback = interrupt({
    "type": "planner_review",
    "message": "请审核研究计划",
    "plan": current_plan,
})

# 恢复点：用户提交反馈后，Command(resume=feedback)恢复图执行
workflow_input = Command(resume=f"[{request.interrupt_feedback}]")
```

**思路**：`interrupt()`暂停图执行并把状态存入checkpoint表，用户在前端审核后提交反馈，后端用`Command(resume=...)`恢复图执行。整个过程对Agent透明——Agent不知道被中断过，只看到`feedback`作为函数返回值。

### 技术亮点

| 亮点 | 说明 |
|------|------|
| **三中断点覆盖全流程** | 计划/报告/检索三处审核，用户可在关键决策点干预AI |
| **interrupt透明恢复** | Agent无感知中断，`interrupt()`返回值即用户反馈，代码简洁 |
| **checkpoint持久化** | 中断状态存PG checkpoint表，支持刷新页面/重启服务后恢复 |
| **skip跳过控制** | `ThreadStateManager`内存单例管理skip标志，双检查点（执行前+执行中）实现即时跳过 |
| **会话回放** | 三分支回放（mock静态文件/thread_id数据库/replay演示），Web Worker控制打字机延时 |

### 实操流程

```
HITL完整流程（以计划审核为例）：

1. 用户提问 → graph开始执行
2. coordinator判断为研究意图 → goto planner
3. planner拆解研究计划 → goto human_feedback
4. human_feedback_node 调用 interrupt()
   → 图暂停，状态存入checkpoint表
   → Layer 3检测到 __interrupt__ → Layer 5打成interrupt SSE事件
   → 前端显示计划审核卡片

5. 用户审核计划：
   方案A：[ACCEPTED] → 接受计划
   方案B：[EDIT_PLAN] + 修改意见 → 重新规划

6. 前端提交反馈 → POST /api/chat/stream（携带interrupt_feedback）
7. Layer 2检测到interrupt_feedback → workflow_input = Command(resume="[ACCEPTED]")
8. graph.astream(Command(resume=...)) → 从checkpoint恢复执行
9. human_feedback_node的interrupt()返回"[ACCEPTED]"
10. goto research_team → 研究员开始执行步骤

任务管理：
┌──────────────────────────────────────────────────┐
│ 1. 制定迭代计划：按章节拆分功能增量（SSE→HITL→skip→回放→可观测→MCP→RAG）│
│ 2. 任务分配：后端3人（API/图节点/工具层），前端2人（SSE消费/配置管理）   │
```

## 项目成果总结

| 能力域 | 交付内容 | 量化指标 |
|--------|----------|----------|
| **SSE流式** | 五层调用链 + 5种事件类型 | 首字延迟<500ms，逐token推送 |
| **可观测** | @timed_node + CB-2连接池 + LLM超时 | 节点耗时100%可见，慢SQL 30s熔断 |
| **MCP工具** | 三层transport + 双层安全门 + 降级 | 工具加载60s超时，失败不影响主流程 |
| **RAG检索** | Retriever抽象 + 6端点CRUD + HITL审核 | 支持内存/AIHub多provider可插拔 |
| **HITL协同** | 三中断点（计划/报告/检索）+ skip控制 | 中断状态PG持久化，刷新可恢复 |
| **会话回放** | 三分支回放 + Web Worker打字机 | 5档速度可调，历史会话可重播 |

**核心架构价值**：通过五层SSE调用链的单一职责分层、Retriever抽象的开闭原则、MCP双层安全门的防御性设计，实现了"可观测、可扩展、可检索"的智能研究平台，新工具/新知识库/新provider接入均无需修改核心流程代码。
